# 三言 AI 伴侣 App · 一期设计文档

- **产品名**：三言 · 3yan
- **释义**：心灵的栖息地
- **创建日期**：2026-05-05
- **目标**：单角色深度调教的 AI 虚拟女友产品，国内市场为主，海外架构预留
- **一期定位**：MVP 内测版，重点验证对话引擎与记忆系统

---

## 1 核心原则

### 1.1 真北星（North Star）

**自己每天主动想打开它聊半小时。**

一期是否成功，不看上线、不看 DAU、不看付费率，只看一个标准 —— 产品负责人自己每天打开它，自然地、没有强迫感地、不出戏地，能聊半小时以上。

推论：

1. **dogfooding 优先**：所有功能先以"我自己用得爽"为最低标准，再谈用户。我自己都不想用的功能，绝不上线。
2. **核心做到 90 分，胜过 5 个功能各 60 分**。上一个 demo 的失败教训 —— 语音消息这种重型功能摊大了精力，结果对话本身做不精，全盘失败。一期反过来：**砍到只剩对话，把对话做到 90 分**。
3. **失去兴趣 = 项目死亡**。开发者自己对项目失去动力，迭代就停了。任何决策都问一句"这事做了，我对项目的兴趣会涨还是降？"

### 1.2 #2 原则：消除 AI 感，模拟真人聊天节奏

具体推论：

| 反 AI 感设计 | 实现方向 |
|---|---|
| **不流式输出** | 后端等 LLM 完整返回，一次性下发整段消息 |
| **"正在输入..."状态** | 收到消息后先显示输入中动画 |
| **模拟打字时长** | 根据消息字数计算延迟（50 字 ≈ 3-5 秒"打字时间"），不要秒回 |
| **拟人化的回复节奏** | 长回复可拆成多条短消息分批发（真人也是"叮叮叮"连发，不是一大段甩脸上）|
| **偶尔的"输入中"取消** | 显示"正在输入..."后又消失（真人打字打到一半删掉重写） |
| **不秒回** | 即使 LLM 已经返回，也加个最低延迟（最快 1.5s 才显示），消除"AI 即时反应"感 |

### 1.3 一期范围控制

**一期只做对话核心**。不做的事：

- ❌ 多角色 / 角色广场 / UGC（深度调教单一个角色）
- ❌ 角色定制 / 用户自建角色
- ❌ 语音消息 / TTS（上一个 demo 教训）
- ❌ Live2D / 动态立绘
- ❌ 多模态（图片发送）
- ❌ 表情切换立绘
- ❌ 流式响应
- ❌ 微信 / 第三方登录
- ❌ 邮箱登录
- ❌ 游客模式
- ❌ 完整变现系统（订阅 / 充值 / 礼物 / 抽卡）
- ❌ 多端同步（一期就有真账号但不专门做跨端实时同步）
- ❌ Apple ID 登录（不接第三方就不需要）

## 3 角色与关系系统

### 3.1 角色设定（一期单角色）

| 维度 | 设定 |
|---|---|
| **暂代号** | 林小满 |
| **身份** | 职场新人 |
| **性格** | 软萌可爱 + 俏皮 |
| **说话风格** | 网络口语（颜文字、网络用语适度） |
| **认识背景** | 网友（自然的"网上聊起来"起点）|

> 一期只有这一个角色，深度调教其 prompt + 长期记忆 + 对话节奏。引擎跑通后，未来加新角色 = 配置新 prompt 数据，无需架构改动。

### 3.2 关系养成 5 阶段

| 阶段 | 亲密度区间 | 称呼 | 说话方式 | 主动性 |
|---|---|---|---|---|
| **陌生人** | 0–100 | "你"、网名 | 礼貌、距离感、偶尔害羞 | 不主动 |
| **朋友** | 100–300 | 真名 / 自定昵称 | 自然、放松、开玩笑 | 偶尔早晚安 |
| **暧昧** | 300–600 | 专属昵称 | 撒娇、试探、害羞 | 主动关心、吃醋 |
| **恋人** | 600–1000 | 老公/宝贝 | 撒娇、依赖、占有欲 | 主动想你、纪念日 |
| **老夫老妻** | 1000+ | 稳定亲密称呼 | 生活感、小吵小闹、深度依赖 | 高频次自然推送 |

每个阶段的具体 prompt 模版、称呼表、话题清单作为**配置数据**存储，不写死在代码里。

### 3.3 亲密度引擎（D 方案）

**行为为主 + 剧情节点 + AI 评估加成**：

| 来源 | 触发 | 增量 |
|---|---|---|
| **基础行为**（每天聊天） | 每条消息（限频）+ 当日首次聊天 +X | +1~+10/条，每日累计封顶 |
| **连续登录加成** | 连续 N 天打开 | 累进奖励（避免长期消失则归零）|
| **关键剧情节点** | 触发条件命中（如连续 3 晚聊到深夜，或对话深度达到阈值）| 一次 +30~+100，伴随剧情演出 |
| **AI 评估加成** | DeepSeek V4-Flash 后台评估对话质量（深度分享、记得对方说过的事等）| +0~+20 |

亲密度变化对用户**显式可见**（顶部进度条），降低"为啥我聊了半天没涨"的困惑。

## 4 对话引擎与长期记忆

### 4.1 长期记忆系统（B + C + RAG 锁死方案）

| 层 | 名称 | 作用 |
|---|---|---|
| **B** | 滚动摘要 | 每隔 N 条消息自动总结一段"对话纪要"，按时间排序入库 |
| **C** | 结构化档案 | 角色一边聊一边自动抽取结构化字段：用户基本信息（姓名/年龄/职业/家乡）、偏好（食物/电影/颜色）、关键事件（生日/纪念日/重要事情）、情感线（吵架/和好瞬间） |
| **RAG** | 向量检索 | 历史对话向量化存入 pgvector，用户提"上次那部电影"时按语义检索相关历史 |

**RAG 范围一期锁死，不调优**（避免重蹈"语音消息做不精"覆辙）：

| 维度 | 一期决策 |
|---|---|
| 向量库 | **pgvector** 扩展（挂在主 Postgres 上，不引入新组件） |
| Embedding 模型 | **BGE-M3**（开源，中英文都强）或 **智谱 embedding-3**（API），二选一，不做 A/B 测试 |
| Chunk 策略 | 按对话轮次组（每 5-10 条消息为一组）|
| 检索 | Top 5，相关性阈值固定（cos sim > 0.6）|
| 调优 | **一期不做**。上线后跑数据，第二期再迭代 |

### 4.2 LLM 选型

| 角色 | 模型 | 价格（¥/1M） | 上下文 | 用途 |
|---|---|---|---|---|
| **主链路对话** | `qwen-plus-character` | 中档 | 32K | 用户感知到的所有对话 |
| **后台任务** | `DeepSeek V4-Flash` | 1 / 2（缓存 0.2） | 1M | 摘要 / 记忆抽取 / 亲密度评估 / 情绪检测 |
| **高端会员（一期不做，架构预留）** | Claude Opus 4.7（中转通道）| 高 | 1M | 未来差异化卖点 |

**LLM Adapter 抽象层**：一期实现 2 个具体适配器（QwenAdapter、DeepSeekAdapter），其他厂商作为接口预留。代码层提供 `LLMProvider.chat(messages, opts)` 统一接口，业务代码不直接调厂商 SDK。

> **重要事实修正**（基于调研）：MiniMax 公开 API 现在主推 Agent/Coding，星野/Talkie 用的是私有 fine-tune 不对外。直接调 MiniMax 公开 API 跑陪伴效果**显著弱于**其 C 端产品。所以一期不选 MiniMax。

> **DeepSeek V4-Pro 75% 折扣到 2026/5/31 截止**，主链路如果要用 V4-Pro 须按 6 月恢复价（¥12/¥24）核算成本。后台用 V4-Flash 不受影响。

### 4.3 内容尺度（L2 暧昧适度）

| 项 | 一期边界 |
|---|---|
| 拥抱、亲吻、亲耳朵 | ✅ |
| 撒娇、轻微吃醋占有欲 | ✅ |
| 暧昧称呼（宝贝/老公）| ✅ |
| "想抱着你睡"等含蓄表达 | ✅ |

## 5 主动消息系统

### 5.1 主动场景（4 个全做）

| 场景 | 触发条件 | 复杂度 |
|---|---|---|
| **a. 早晚安问候** | 用户设定时间或默认时间 | 低 |
| **b. 失联召回** | 用户连续未打开 24h / 3天 / 7天 阶梯式发送 3 条递进语调的"想你了"消息（关心 → 撒娇 → 占有欲） | 低 |
| **c. 重要事件追问** | 用户聊过的事件次日自动问候（"明天面试" → "今天怎么样"）| 中 |
| **d. 情境关怀** | 检测到用户情绪低落（深夜倾诉 / 关键词），第二天主动关心 | 中 |

**情绪检测和事件抽取走 DeepSeek V4-Flash**，便宜、不需要拟人。

### 5.2 可靠性投递（4 层兜底）

**核心原则：先落库、再分发。WebSocket 只是快速通道，不是可靠通道。**

```
1. 后台任务命中 → 写入 messages 表（status=pending）
2. 查 Redis：用户在线吗？
   ├─ 在线 → WebSocket push（带 message_id）
   │  ├─ 客户端 ACK → status=delivered ✅
   │  └─ 5s 没 ACK → 当离线，转下一步
   └─ 离线 → APNs / 个推 → status=push_sent
3. 用户下次打开 app → HTTP /sync?since_id=xxx
   └─▶ 拿到所有 status != read 的消息 ✅（终极兜底）
```

L4（客户端启动拉取）保证 100% 不丢消息。推送通道的真实价值是"提醒用户来打开 app"，不是"保证送达"。

## 6 通信架构

| 通道 | 用途 | 协议 |
|---|---|---|
| **WebSocket（主链路）** | App 前台时所有消息：用户发 → 她回 + 她主动 | WS + 简单 JSON 帧（不用 STOMP） |
| **HTTP REST（辅）** | 登录鉴权、历史消息分页（/sync）、用户档案、亲密度查询、设置 CRUD | RESTful |
| **APNs / 个推** | App 后台/退出时她的主动消息 | 各平台 SDK |

### 6.1 WebSocket 关键参数

| 配置 | 值 | 理由 |
|---|---|---|
| 客户端 Ping 间隔 | 30s | 短于运营商 4G/5G NAT 5-10 分钟超时 |
| 服务端会话超时 | 60s（连续 2 次没收到心跳）| 双倍间隔避免单次抖动误判 |
| 断线重连 | 指数退避（1s→2s→5s→10s→30s→30s...）| 客户端检测到 close 立即首次重连 |
| 单实例连接数 | 上限 5000（一期单机够用）| 超过则横向扩展 |

### 6.2 多实例下的连接路由

`Redis: user_id → instance_id + connection_id` 维护映射。后台任务发主动消息时通过 `Redis Pub/Sub` 通知"消息发给 user X" → 持有 user X 连接的实例转发到 WS。

## 7 用户体系

### 7.1 注册与登录

| 路径 | 用途 | 国内 / 海外 |
|---|---|---|
| **手机号 + 短信验证码** | **注册必走 + 登录主路径** | 国内 ✅ |
| **手机号 + 密码** | 登录辅助路径（用户设密码后可用） | 国内 ✅ |
| **邮箱 + 密码** | 一期不做，**用户表预留 `email VARCHAR(120) NULL UNIQUE` 字段** | — |
| **微信 / Apple ID / 第三方** | 一期不接 | — |

> **合规依据**：《生成式人工智能服务管理暂行办法》要求实名。手机号 = 运营商已实名 ✓。
>
> **Apple 4.8 规则**：仅当 app 接入第三方/社交登录时才必须同时提供 Sign in with Apple。一期不接第三方，故不需要 Apple ID 登录。

### 7.2 一期不做"启动即聊"匿名模式

虽然"启动即聊"能省下 2-3 周登录系统工作量，但用户决策保留登录系统。理由：上线前必须补登录的工作（数据迁移）成本反而更高。

### 7.3 变现（一期架构预留）

| 项 | 一期决策 |
|---|---|
| **付费功能** | 一期不实现 |
| **用户表字段** | 预留 `subscription_status`、`subscription_expires_at`、`daily_quota_used` 等字段 |
| **付费墙** | 一期不存在 |
| **上线前可能补订阅** | 用户表态"上线前可能加最简订阅"，架构留空给二期或上线前增量 |

## 10 数据基础设施

| 组件 | 选型 | 用途 |
|---|---|---|
| **主数据库** | **PostgreSQL 15+**（自建在 ECS 上） | 关系数据 + 向量数据（pgvector）|
| **向量扩展** | **pgvector** | 挂在主 Postgres，不引入独立向量库 |
| **缓存** | **Redis 7+**（自建在 ECS 上） | WS 连接状态、JWT 黑名单、热数据缓存、限流 |
| **消息队列** | **Redis Streams** | 异步任务（摘要、记忆抽取、推送调度） |
| **对象存储** | **腾讯云 COS**（已有 50G 免费额度）+ CDN | 角色立绘、用户头像、PostgreSQL 每日备份 |
| **全文搜索** | 一期不做 | 用户不需要搜索历史聊天功能 |

### 10.1 内存预算（4C4G 单机）

| 进程 | 内存 |
|---|---|
| Spring Boot 应用 | `-Xmx 1500M`（G1GC） |
| PostgreSQL | `shared_buffers 512M`，`work_mem 16M`，`maintenance_work_mem 128M` |
| Redis | `maxmemory 256M`，`maxmemory-policy allkeys-lru` |
| Nginx + 系统 + buffer | ~600M |
| **合计** | **~3GB**（剩 1G 给 OS buffer/cache） |

承载力估算：≤ 50 内测用户充足；50-200 种子用户需监控；> 200 须扩容（首选拆 PostgreSQL 到云数据库）。

### 10.2 数据备份（不可省）

**每日 03:00 cron** 执行：

```
pg_dump → gzip → 上传 COS（保留 30 天）
```

单机部署 + 单点 PostgreSQL 没备份就是定时炸弹。备份实现失败会被持续告警。

## 附录 A：决策溯源（这一期的几个关键判断）

1. **从"启动即聊"切回"必须登录"** —— 用户初始想砍掉登录加速 MVP，但考虑上线前补登录的数据迁移成本，最终保留登录系统。
2. **从"流式响应"切到"完整消息 + 真人节奏模拟"** —— 用户判断"流式破坏 AI 拟人感"，反而让后端架构简化（不需要 WebFlux）。
3. **从"HTTP 一次性响应"切到"WebSocket 双向通道"** —— 用户判断"主动消息必须服务端能 push"，HTTP 单向不够。
4. **从"E（B+C）一期记忆方案"切到"D（B+C+RAG）一期方案"** —— 用户判断 RAG 是核心体验不是花活；范围一期锁死不调优避免重蹈覆辙。
5. **从"MiniMax 主链路"切到"qwen-plus-character 主链路"** —— 调研发现 MiniMax 公开 API 不等于星野体验，且阿里 character 系列是当前更对路的方案。
6. **从"接 OpenAI 走个人订阅 + VPS"切到"国内合规模型"** —— 用户提议被合规风险否决，确认国内主链路必走备案模型。
7. **从"Vela / Nyra 英文短词命名"切到"三言中文为主"** —— 英文短词在 AI 时代被抢光，中文命名空间空白多，且策略上国内为主。

## 附录 B：本一期不解决的"已知未知"

- **Embedding 模型选 BGE-M3 还是智谱 embedding-3** —— 实现阶段对比一次后定型，不做长期 A/B
- **客户端"模拟打字时长"具体公式** —— 实现阶段调试找到"自己用得最舒服"的延迟系数
- **亲密度数值具体增量** —— 实现阶段调试，按"自己玩 1 周后体感对不对"调整
- **个推 vs 极光 vs 厂商通道** —— 推送通道选型在实现阶段定（看哪家 Java SDK 文档好 + 单价低）
- **JWT secret / API key 等敏感配置** —— 用 `.env` + 不提交（按 `~/.claude/rules/java-backend*.md` 既定规范）

这些都是"实现阶段的小决策"，不是 spec 层面的设计问题。
